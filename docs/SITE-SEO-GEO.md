## География и аудитории

Решение владельца 1 октября 2026: долгосрочная цель международная, первый этап
для русскоязычной аудитории стран СНГ. Это язык и география исследования спроса,
не заявление о доступности всех услуг, оплат или операторов во всех странах.
Используем существующий `/ru/`, без копий одинаковых статей для каждой страны.
Казахский язык остаётся следующим согласованным направлением; другие переводы
и региональные версии готовим после исследования, не объявляем заранее.
Для будущих реальных переводов предусматриваем отдельные URL и `hreflang`,
без автоматического перенаправления посетителей по предполагаемому языку.
Это соответствует [рекомендациям Google по языковым версиям](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites).

Два отдельных направления контента:

- Medina OS: владельцы и управляющие салонов, стоматологий, клиник. Темы про
  запись, обработку обращений, работу операторов и понятный рекламный учёт.
- Сайты клиник/салонов: их будущие пациенты и клиенты. География, услуги и цены
  только конкретного согласованного бизнеса. Медицинские утверждения требуют
  проверки профильным специалистом; имя эксперта и результаты не выдумывать.
  Сейчас готовим только подход, не создаём страницы в рабочих пространствах.

## База поисковых запросов

1 октября получено первое локальное наполнение: 12 наблюдений отчётов и 136
строк их таблиц, [исходные данные](seo-research/2026-10-01-wordstat.json).
Это чтение интерфейса после входа, не API-интеграция и не подтверждённая полная
CSV-выгрузка. Собственный сборщик и платный сервис не создавались/не подключались.
Wordstat поддерживает регионы, периоды и CSV; ему нужен вход в Яндекс.
Его число запросов нельзя выдавать за суммарный спрос Google и Яндекса.
[Документация Wordstat](https://yandex.ru/support2/wordstat/ru/interface/new).

Одна запись замера содержит:

| Поле | Правило |
| --- | --- |
| Запрос и режим | Исходная фраза, операторы/тип соответствия; не подменять широкую частотность точной |
| Аудитория и ниша | Владелец бизнеса или пациент/клиент; салон, стоматология, клиника |
| Язык и регион | `ru`, выбранная страна/регион и идентификатор из источника; «весь мир» хранить отдельно |
| Источник | Сервис и поисковая система; ссылка на отчёт или локальная исходная выгрузка без секретов |
| Время | Дата получения и период, за который рассчитан показатель |
| Показатель | Тип метрики, значение, фильтр устройств; неизвестное значение не равно нулю |
| Намерение и проблема | Что человек хочет решить, а не только слова запроса |
| Группа и страница | Одна основная страница на общее намерение; новая статья или доработка существующей |
| Статус | Гипотеза, спрос проверен, задание, черновик, проверен, опубликован, требует обновления |

Замеры разных стран, периодов, операторов и систем не складываем. Пересекающиеся
широкие запросы тоже не суммируем как уникальный спрос. Отсутствие доступа/данных
фиксируем явно. Поисковые подсказки годятся для гипотез, но не заменяют частотность.
После выпуска статистику собственного сайта добавляем отдельно от рыночного
спроса: запрос, страница, страна, показы, клики и обращения при проверенном учёте.
«Спрос проверен» означает наличие наблюдения для конкретной фразы, системы,
региона и периода, а не подтверждение бизнес-намерения всех найденных запросов.

## Последовательность контентной работы

1. Собрать первую проверяемую выборку запросов по трём нишам, с отдельными
   срезами стран. Не ждать запуска сайта для исследования спроса.
2. Объединить близкие запросы по задаче читателя и сопоставить с тремя готовыми
   материалами. Сначала углублять существующий ответ, если новая тема дублирует его.
3. Выбрать небольшую первую партию по спросу, связи с услугой и возможности дать
   самостоятельное решение. Не назначать вымышленную конкурентность или прогноз трафика.
4. На каждую статью подготовить задание: боль, вопрос, короткий ответ, причины,
   конкретные действия, полезный шаблон, источники и уместный следующий шаг.
   Проверка фактов и смысла обязательна; генерация не равна публикации.
5. Публиковать только проверенные и разрешённые снимки после S4. Проверять
   доступность и индексацию, затем улучшать статьи по наблюдаемым результатам.

Количество статей не служит критерием готовности. Цель: покрыть полезные задачи
аудитории и получать релевантные обращения. Не обещать топ, сроки или отсутствие
необходимости редакционной проверки. [Ориентир Google по полезному контенту](https://developers.google.com/search/docs/fundamentals/creating-helpful-content).

## Подготовленные изменения

- Короткий самостоятельный ответ в начале каждого материала; затем разбор боли,
  примеры, конкретные действия и шаблон. Основные термины в естественном тексте,
  не в списке повторов ключевых слов.
- Уникальные title/H1/description, HTML без необходимости исполнять JavaScript,
  canonical без рекламных query-параметров. Русский язык; казахские страницы
  не объявляются через hreflang до появления перевода.
- BlogPosting, Organization-автор Medina OS и BreadcrumbList через Microdata.
  Разметка совпадает с видимым текстом и сохраняет `script-src 'none'`; вымышленных
  персональных авторов, рейтингов и скрытых FAQ нет.
- Дата последней разрешённой редакции берётся из `published_at`, не из даты сборки,
  текущих часов или `updated_at` черновика. Она отображается в статье и lastmod
  sitemap. Исходная первая дата публикации отдельно не хранится, поэтому
  `datePublished` не выдумывается. Без реальной валидной даты поле отсутствует.
- «Читайте также» строится только из разрешённых серверных снимков; снятая статья
  не остаётся ссылкой. Есть переходы на направления, услуги и форму.
- Open Graph определяет статью и бренд; изображение — существующий логотип,
  не вымышленный кейс. Индексация остаётся под явным серверным флагом.

## Порядок публикации после доступа

1. Проверить текущий проект/deployment, owner и именно маркетинговое пространство.
   Не переключать права/сессии сотрудников салонов и не использовать их данные.
2. Убедиться в поддержке опубликованных снимков. Сохранить три текста через
   существующий редактор, проверить предпросмотр, явно разрешить каждый снимок.
   Не импортировать README, тестовые примеры или все локальные документы.
3. Перед runtime-выпуском пройти безопасный preview и auth-регрессии. Применение
   миграций, включение неподготовленной формы и удаление данных не следуют из
   разрешения опубликовать статьи. Форму не выдавать за рабочую без её приёмки.
4. Для разрешённого выпуска проверить origin, публичный gate, доступ поиску,
   robots/canonical/sitemap. Корень CRM не перенаправлять, закрытые страницы
   и API не открывать роботам. Не публиковать secrets или данные рабочих пространств.
5. Проверить все три URL, HTML, CSS/логотип, мобильную вёрстку, ссылки, дату,
   отсутствие noindex на разрешённых страницах и 404/noindex на неизвестных.
6. С доступом владельца добавить URL-prefix property в Google Search Console,
   подтвердить владение и отправить `/ru/sitemap.xml`. При необходимости отдельно
   подключить Яндекс Вебмастер/Bing. Это не сделано автоматически и не означает
   индексацию. Проверять показы/запросы/клики, а не обещать результат заранее.
