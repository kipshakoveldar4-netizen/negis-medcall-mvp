# Сайт и блог Medina OS

## Согласованные решения

- Сайт внутри текущего проекта, без второй CRM и базы клиентов.
- Бренд Medina OS; аудитория: салоны, стоматологии и клиники.
- Сначала русский язык, затем казахский.
- Основной призыв: «Оставить заявку», не WhatsApp.
- Отдельное пространство «Medina OS — маркетинг», владелец eldar@mail.ru.
- medinaos.kz — кандидат, доступность и покупка пока не подтверждены.
- Демонстрационные кейсы только в закрытом предпросмотре с явной пометкой;
  публичные результаты, отзывы и кейсы требуют подтверждения владельца.

## Подготовка пространства

В Medina Control форма подключения поддерживает назначение «Маркетинг и
привлечение клиентов». Оно хранится в `workspace_settings` под ключом
`workspace_purpose`, значение `{ "purpose": "marketing" }`. Новая таблица
или миграция не нужна. Это назначение CRM, не рекламная ниша и не право доступа.

Для этого назначения доступно только приглашение: существующий пользователь
принимает его своим аккаунтом. Пароль и существующие членства не меняются.
Создание остаётся за `requirePlatformOwner`; владелец клиники самовольно
создать пространство через этот маршрут не может. Дополнительное пространство
для одной почты требует существующего явного подтверждения. Публичная
саморегистрация не включается.

Маркетинговому пространству не записывается выдуманная медицинская ниша.
Существующая рекламная политика НЕ ослабляется: пока специальная рекламная
политика не реализована, отсутствие ниши оставляет консервативную проверку.
Старые CRM-экраны ещё могут показывать медицинские подписи по умолчанию.
Назначение само по себе не подключает сайт, тариф, форму заявок или рекламу.
Поддержка опубликована в `ed976b5`. Пространство создано через production
Medina Control. По отдельному разрешению владельца существующий подтверждённый
аккаунт eldar@mail.ru привязан напрямую как активный owner; неиспользованное
приглашение отозвано. Вход и админ-доступ проверены в браузере для пространства
1556034a-7a67-4ceb-b3c9-9748e53e588f. Пароли и членства других пространств не менялись.
Токен приглашения не сохраняется в документации.

## Локальный предпросмотр сайта

`artifacts/medina-site` содержит статический HTML-генератор без новых зависимостей:
главную, четыре услуги, список блога, два редакционных черновика и HTTP 404.
Используется существующий логотип Medina OS. Новые API, таблицы и настройки
деплоя не добавлены; маршруты входа и CRM не изменены.

Запуск: `node artifacts/medina-site/dev.mjs` (127.0.0.1:5186/ru/).
Сборка: `node artifacts/medina-site/build.mjs`.
Проверки: `node --test artifacts/medina-site/site.test.mjs`.

Это ещё не опубликованный сайт и не CMS. Индексация закрыта через robots и
метаданные; локальный сервер также возвращает X-Robots-Tag. Форма полностью
отключена и не передаёт данные. Перед публикацией нужны защищённый приём заявок,
согласие на обработку данных, редакционная проверка, домен и SEO-настройки.
Управление статьями из кабинета, canonical и sitemap пока не реализованы.

## Основа приёма заявок (058, ещё не включена)

Миграция `058_public_site_intake_foundation.sql` добавляет только серверные
таблицы `crm_intake_sites` и `crm_site_inquiries` и RPC `accept_crm_site_inquiry`.
Не создаёт привязок сайта, не включает приём и не меняет существующие записи.
По умолчанию сайт выключен. Применение миграции само по себе форму не оживляет.

Пространство определяется только по серверной привязке `site_key`. В форме нет
workspaceId, clientId, leadId, рекламных идентификаторов или произвольных полей.
Допустимы имя, телефон, организация, одно из четырёх направлений, путь страницы
без query/hash и явное согласие с версией текста. Телефон нормализуется общим
CRM helper и отдельно проверяется. Медицинские сведения форма не собирает.

Серверная функция проверяет страницу и версию согласия по настройке сайта.
Под блокировкой строки сайта она сохраняет заявку CRM и подтверждение согласия
в одной транзакции. Повтор с тем же request_key возвращает тот же безопасный
ответ; изменение данных под этим ключом отклоняется. Повтор с новым ключом и
точно теми же именем, телефоном, организацией и услугой в течение суток может
использовать ту же заявку сайта. Исторические CRM-заявки не перезаписываются.
Источник «Сайт» и начальный этап берутся из справочников своего пространства.

Ограничения по умолчанию: 100 новых отправок на сайт за час, 5 на телефон за
сутки. Это транзакционные ограничения хранения, **не полноценная антибот-защита**.
Точный повтор уже сохранённого запроса лимит повторно не расходует.
Персональные данные находятся в закрытой таблице согласий и в CRM, не в ответе.
RPC возвращает только `{ accepted: true }`, без контактов и внутренних ID.
RLS включён, anon/authenticated не могут читать таблицы или вызывать RPC.
Вызов предназначен только для серверного service_role.

До публичного подключения обязательны:
- ограниченный по размеру серверный адаптер внутри существующего API;
- проверенная серверная привязка домена/сайта (не tenant из браузера);
- антибот-проверка и ограничение запросов на внешней границе;
- согласованный текст согласия, версия и путь политики;
- безопасные ответы без ошибок БД, контактов и токенов;
- учёт `crm_site_inquiries` в удалении персональных данных и политике хранения;
- проверка формы и доставки в нужное пространство, затем отдельное включение.

Изолированный маршрут описан ниже; обычные CRM-ресурсы по-прежнему требуют
авторизации, старый webhook остаётся закрытым. UTM и аналитика отложены до отдельной
санитизации; полные URL и произвольные payload не сохраняются.

Тесты: `pnpm --filter @workspace/scripts run test:site-intake` выполняют SQL
в изолированном PGlite и проверяют права, изоляцию пространств, согласие,
повторы, лимиты и транзакционный откат. Production этими тестами не затрагивается.
PGlite не заменяет будущую проверку параллельных транзакций в PostgreSQL.

## Подключение формы (код готов, включение отдельно)

`POST /api/crm/site-inquiry` внутри существующего catch-all принимает только
requestKey UUID v4, inquiry и challengeToken. Нет GET со сведениями о заявках,
нет выбора workspace/site посетителем. Путь с дополнительными сегментами — 404.
Настройки отсутствуют — 503, без обращения к провайдеру или БД.
Тело ограничено 8 КБ до разбора JSON. Верифицируются точный Origin, одноразовый
Turnstile token, hostname и action `site_inquiry`. Ошибка проверки закрывает
запись. Права владельцев CRM и HMAC работников не заменяются этим механизмом.

Серверные переменные в защищённых настройках API deployment (не в браузере):
- `MEDINA_SITE_INTAKE_ENABLED=true` — только после всех проверок готовности;
- `MEDINA_SITE_ORIGIN` — точный HTTPS origin сайта без пути/слэша;
- `MEDINA_SITE_INTAKE_KEY` — ключ включённой строки crm_intake_sites;
- `MEDINA_SITE_TURNSTILE_SECRET` — секрет Turnstile; не присылать в чат;
- существующие Supabase server env.

Публичные переменные **сборки сайта**, не секреты:
- `MEDINA_SITE_FORM_ENABLED=true`;
- `MEDINA_SITE_API_ORIGIN` — HTTPS origin CRM API;
- `MEDINA_SITE_TURNSTILE_SITE_KEY` — публичный site key виджета;
- `MEDINA_SITE_CONSENT_VERSION` — версия, совпадающая с настройкой сайта.

Без явного включения сборка сохраняет отключённую форму и не загружает
Cloudflare. При включении посетитель подтверждает согласие, получает challenge,
затем запрос передаётся прямо API без cookie/пользовательского Bearer.
Секрет, имя и телефон не отправляются друг другу: Cloudflare получает только
challenge token и серверный secret, без содержимого заявки и явного remoteip.
Сам виджет является сторонним сервисом; это необходимо отразить в политике.
Проверка описана в [официальной документации Turnstile](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

Повтор после сетевой ошибки сохраняет requestKey до изменения полей и требует
свежего challenge. Успех показывается только после HTTP success и `success:true`.
Ошибка БД или пустой ответ не превращаются в успех. Контакты остаются только
в памяти формы до ухода со страницы; localStorage и URL для них не используются.

Перед включением требуется применить 058, отдельно настроить строку сайта на
нужное пространство с разрешёнными страницами/версией согласия, настроить
Turnstile только на подтверждённый домен и edge/WAF rate limiting.
60 проверок в минуту на экземпляр API — лишь дополнительный локальный
предохранитель, не распределённая защита. Лимиты базы сохраняются независимо.
Нужно также проверить удаление согласий по запросу владельца данных и текст
политики, после чего провести согласованную проверку доставки тестовой заявки.
Ничего из этого не применяется автоматически этим коммитом.

Файлы сборки остаются `noindex`: отдельный hosting/deployment и индексация
пока не подключены. При отдельном hosting перенести CSP из dev.mjs в headers
deployment: скрипты/iframe только self и challenges.cloudflare.com, connect-src
дополнительно точный API origin, form-action none. Не разрешать wildcard.
Секретов Turnstile в тестах нет: провайдер и записи БД подменяются тестовыми
реализациями, а SQL отдельно выполняется в PGlite.
