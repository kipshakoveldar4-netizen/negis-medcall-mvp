# Миграции: воспроизводимая цепочка

**Воспроизводимая цепочка начинается с `009_medcall_mvp_persistence.sql`.**
Файлы `001–008` — исторический архив: они писались для вставки в SQL Editor
поверх уже работавшей базы и на пустой базе не исполняются. Новые среды
собираются цепочкой 009+; набор `test:migration-chain` (M1–M4) держит её
самодостаточной и падает, если новая миграция это нарушит.

Это зафиксированный вариант A. Он ничего не закрывает: если когда-нибудь
понадобится историческая полнота, `000_legacy_baseline.sql` (вариант B) можно
написать позже — с учётом перечисленных ниже расхождений.

## Почему 001–008 не исполняются на пустой базе

Шесть таблиц упоминаются в 001–006 и не создаются ни одной миграцией:
`agents`, `clinics`, `lead_statuses`, `booking_statuses`, `services`,
`bookings`. Все шесть имеют **0 ссылок в рабочем коде** — сервер работает
с таблицами, создаваемыми в 009+. `user_roles` выглядит седьмой, но ALTER
в `008:44` стоит за `to_regclass('public.user_roles') IS NOT NULL` и на
пустой базе не выполняется (закреплено M4).

## Известные расхождения production и цепочки

Production собирался исторически, через SQL Editor, поэтому три факта его
схемы не выводятся из каталога `migrations/`:

1. **Шесть таблиц выше** существуют в production и не создаются цепочкой.
2. **`chat_messages` определена в цепочке дважды и несовместимо** —
   `005:56` (`clinic_id → clinics`, `conversation_id`, `sender_agent_id`,
   `body`) и `010:90` (`workspace_id → workspaces`, `channel`,
   `sender_name`, `sender_role`, `message`). Обе `CREATE TABLE IF NOT
   EXISTS`: при прогоне 001→025 молча победила бы форма 005, а сервер
   (`lib/crm/server.ts`, ресурс `chat`) работает с формой 010. Production
   имеет форму 010. Коллизия записана с обоснованием в M2.
3. **`leads.assigned_to`** добавляется только в `001:20`
   (`REFERENCES agents(id)`) — целиком в архивном диапазоне. В production
   колонка есть; на чистой базе из 009+ её не будет. Обращений в коде — 0.

## Правила для новых миграций

Кратко (полные требования — в каноническом контексте проекта):
выполняются как postgres; owner = postgres; RLS включается явно;
grants для `anon`/`authenticated` = 0; **grants для `service_role`
задаются явно** — таблица, созданная postgres, их не наследует;
SECURITY DEFINER только с фиксированным `search_path`.

**Применённые миграции не переписываются.** Ошибка в применённой миграции
исправляется следующей по номеру forward-миграцией (прецедент: 024 → 025).
Это закреплено `test:security1b` (26–28) и `test:migration-chain`.
