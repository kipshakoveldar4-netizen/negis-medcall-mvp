# WhatsApp Cloud API — входящие лиды (§14, фаза 2)

Официальный Cloud API от Meta вместо Wazzup: пациент пишет на номер клиники →
Meta присылает вебхук → лид в CRM той клиники, которой принадлежит номер.
Выбор подключения, условия Meta и возможного провайдера согласуются отдельно.
Эта инструкция не разрешает подключать платный тариф, включать исходящие или
расходовать бюджет.

Контракт вебхука — из документации Meta (developers.facebook.com:
`/docs/graph-api/webhooks/getting-started`,
`/docs/whatsapp/cloud-api/webhooks/payload-examples`), не из памяти.

## Номер уже работает в WhatsApp Business на телефоне

Владелец повторно подтвердил обязательное сохранение WhatsApp Business на
телефоне, как в формате Coexistence Wazzup. Выбранный провайдер остаётся прямой
Meta через Negis: упоминание Wazzup описывает ожидаемый режим, не покупку/
подключение Wazzup. В подготовке `connectionMode=coexistence`, `allowApiOnly=false`.
Перенос в API-only не является запасным способом завершить этот запрос.
Не удалять приложение/аккаунт на телефоне, не отвязывать номер, не регистрировать
его обычным API-only мастером. Поддержка подтверждается только после официальной
приёмки: новые входящие в CRM и отправка/приём на том же номере в приложении,
без проверки на рабочих клиентах и без импорта старых чатов/исходящих из CRM.
Эти поля не реализуют Embedded Signup и не гарантируют сохранность всех функций
или связанных устройств: ограничения выбранного потока сначала согласовать.

Проверено 12 октября 2026 по [официальной документации Meta](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users):
режим Coexistence позволяет сохранить приложение на том же номере. Для него
нужны Solution Partner / Tech Provider, совместимая встроенная регистрация
и подтверждение компанией на телефоне. Meta предупреждает об отключении
Embedded Signup v2/v3 с 15 октября 2026; для нового подключения проверять v4.
Часть функций и связанных устройств меняется: согласовать это до подключения.

В этом репозитории реализован приём `messages`, но нет встроенной регистрации
Coexistence и обработки `account_update`, `history`, `smb_app_state_sync`,
`smb_message_echoes`. Обычная привязка `phone_number_id` не выполняет такой
онбординг и не доказывает работоспособность номера. Пока эти требования не
закрыты, подключение с сохранением телефона не считается готовым.

Для Baspana выбран только первый этап: новые входящие заявки, без ответов из
CRM. Не удалять WhatsApp Business, не переносить номер в API-only, не
синхронизировать старые контакты/чаты и не оформлять платного провайдера без
отдельного согласования. Не использовать тестовую базу/Preview для реальных
заявок. Рабочий выпуск, целевое пространство и права команды подтверждаются
до любых облачных изменений; пароль, OTP и секреты не передаются через чат.

## Как устроено

- **Маршрут**: `api/webhooks/whatsapp.ts` → `lib/whatsapp-cloud/webhook.ts`.
  GET — рукопожатие подписки: `hub.challenge` отдаётся только при совпадении
  `hub.verify_token` с `WHATSAPP_VERIFY_TOKEN` (сравнение в константное
  время); иначе 403 без деталей, а без env — 503 fail-closed.
- **Подпись**: каждый POST проверяется по `X-Hub-Signature-256` —
  HMAC-SHA256 от **сырого тела** запроса ключом `WHATSAPP_APP_SECRET`,
  до какого-либо парсинга. Entry point читает именно сырые байты потока
  событийным API и не трогает `req.body`: хелперы @vercel/node возвращают
  буферизованные байты в поток (`restoreBody`), а пере-сериализованный JSON —
  не то, что подписывала Meta (`\uXXXX`-эскейпы кириллицы не совпадут).
  Нет заголовка / не совпал — 401 без деталей. БД недоступна — 503,
  Meta ретраит сама.
- **Ядро общее с Wazzup**: `lib/crm/inbound-whatsapp.ts` — леджер
  идемпотентности → арендатор → дедуп по телефону → воронка → лид. Оба
  адаптера зовут один и тот же код; Wazzup-путь работает как прежде и
  остаётся фолбэком, пока вы сами его не отключите.
- **Арендатор**: только по строке в `whatsapp_cloud_numbers`
  (`migrations/027`): `phone_number_id` из `metadata` вебхука → workspace.
  Payload про клиники не спрашивают. Неизвестный или выключенный номер —
  200-и-игнор, без раскрытия.
- **Идемпотентность**: `whatsapp_cloud_inbound_messages.message_id` (wamid)
  уникален; повторная доставка — no-op.
- **Статусы** (delivered/read) приходят тем же вебхуком — подтверждаются
  без записи.
- **ПД при сбое обработки**: журнал содержит только фиксированное событие
  `[whatsapp-cloud] webhook processing failed`, без текста или сериализации
  исключения. Ошибка базы может содержать значения строки или секреты, поэтому
  её детали не записываются. Ответ остаётся общим 503 `Service unavailable` для
  повторной доставки. Та же граница действует в Wazzup-адаптере. Локальные
  регрессии проверяют синтетические данные в ошибках поиска и отказ произвольным
  объектом; 13 октября оба набора прошли 56/56. Это не проверка облачного канала.

подтверждения на телефоне и принятие условий выполняет владелец.

   разрешения; эта инструкция не разрешает выполнять SQL в рабочей базе.

2. **Meta App**: подтвердить изоляцию приложения и подписки тестового канала.

## Диагностика

- Verify and save падает → проверить совпадение verify token, scope точного
  разрешённого Preview и его выпуск, без раскрытия значений и без переключения
  на Production. При пустом env сервер отвечает 503 — Meta покажет ошибку.
- Сообщение отправлено, лида нет → читать `whatsapp_cloud_inbound_messages`:
  строка есть, лида нет — падение конвейера после леджера (дефект, чинит
  сессия); строки нет — вебхук не дошёл: проверить подписку на поле
  `messages` и привязку номера (шаг 6) — неизвестный `phone_number_id`
  игнорируется молча, это специально.
- Повторные сообщения того же человека лида не плодят — `kind='repeat'` в
  леджере, как у Wazzup.
