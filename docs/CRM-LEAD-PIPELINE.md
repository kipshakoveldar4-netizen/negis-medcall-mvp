# CRM Lead Pipeline

CRM6 добавляет структурированные этапы и источники заявок в Negis OS. Справочники принадлежат конкретному `workspace_id`, поэтому клиники могут развивать свою воронку без смешивания данных между пространствами.

## Migration

Примените `migrations/019_crm_lead_pipeline_foundation.sql` после migrations 009, 010 и 014. Migration:

- создаёт `lead_stages` и `lead_sources`;
- добавляет в `leads` nullable-поля `stage_id`, `source_id`, `meta_campaign_launch_id`;
- создаёт индексы для workspace-scoped выборок;
- добавляет дефолтные справочники существующим и новым workspace;
- безопасно связывает старые текстовые данные со справочниками.

## Этапы по умолчанию

| Ключ | Название | Semantic group |
| --- | --- | --- |
| `new` | Новая | `new` |
| `in_progress` | В работе | `in_progress` |
| `booked` | Записана | `booked` |
| `postponed` | Отложена | `postponed` |
| `lost` | Потеряна | `lost` |

После подготовленной `080_postponed_lead_stage.sql` пользовательские этапы
относятся к одной из пяти semantic-групп. Историческая 019 по-прежнему создаёт
первые четыре; она не переписывается. 080 расширяет ограничение и будущие
значения по умолчанию, но не заполняет существующие пространства глобально.
Для уже существующего пространства требуется отдельно согласованное добавление
только нового этапа по явному списку ID. Общий `seed_default_lead_taxonomy`
может также добавить отсутствующие другие этапы/источники, поэтому для узкого
выпуска его не вызываем; пользовательские строки не перезаписываем.
22 октября 2026 года 080 сначала применена только к `medina-os-site-test`,
этап добавлен только пространству «Medina OS — тест блога».
23 октября по отдельному разрешению 080 применена к `medcall-negis-crm`:
добавлены только пять postponed-этапов, по одному пяти существующим пространствам.
Прежние этапы, источники, заявки, настройки и права не менялись; COMMIT и
исходные контрольные суммы подтверждены независимым read-only postflight.

В отдельном Preview `90036fd` проверены создание одной вымышленной отложенной
заявки через `/leads`, сохранность после reload и фильтр. SQL подтвердил
`status=postponed` и правильный `stage_id`. Заявка и её аудит удалены,
исходные данные/права сверены; подробности G2-C14 в DELIVERY-CYCLES.md.

В ипотечной карточке клиента изменение статуса теперь разрешает настоящий
активный этап текущего пространства и передаёт `stageId`; сервер сам выводит
текстовый `status`. Неизменённый статус не отправляется, поэтому обычная правка
контактов сохраняет пользовательский этап. В отдельном тестовом Preview
`67416e9` принят путь «Новая → Отложена → В работе» через карточку на desktop/mobile,
с reload, фильтром и SQL-сверкой обоих полей. Вымышленные данные и временный
ипотечный профиль убраны; рабочая база не менялась. Подробности G2-C15.

Оба изменения опубликованы 23 октября отдельным рабочим **de97fb6** от ec69a64
на medinaos.com и прежнем проектном адресе CRM. Рекламная цепочка Preview и
остальные накопленные доработки не включались. Проверен рабочий read-only UI
администратора Baspana на desktop/mobile; существующие заявки не изменялись
для проверки. Подробности и границы приёмки G2-C16 в DELIVERY-CYCLES.md.

«Отложенные» имеют отдельные счётчик, фильтр и столбец аналитики. Они не
попадают в «Новые», «В работе» или «Потеряны». Конверсия в запись остаётся
отношением записанных ко всем назначенным, включая отложенные; статус сам
по себе не подтверждает встречу, договор, оплату или расход рекламы.

## Источники по умолчанию

`Вручную`, `Meta Ads`, `Instagram`, `WhatsApp`, `Сайт`, `Рекомендация`, `Webhook`, `Другое`.

Неизвестные исторические значения не теряются: migration создаёт workspace-scoped источник `legacy_<hash>` с исходным отображаемым названием.

## Совместимость

Поля `leads.status`, `leads.source` и `leads.campaign` остаются в схеме и не переписываются во время backfill. Они служат snapshot-полями для старых клиентов, demo/localStorage и pre-migration данных.

При записи через API используется dual-write:

- `stageId` сохраняется в `stage_id`, а `status` получает `stage_key`;
- `sourceId` сохраняется в `source_id`, а `source` получает название источника;
- `metaCampaignLaunchId` сохраняется только после workspace-проверки, а `campaign` получает точное название запуска.

Строковый create/update без структурированных IDs продолжает работать.

## API

Новые ресурсы обслуживает существующий catch-all `api/crm/[...path].ts`:

- `GET|POST|PATCH /api/crm/lead-stages`
- `GET|POST|PATCH /api/crm/lead-sources`
- `GET|POST|PATCH /api/crm/leads`

Удаление справочников не используется. Для архивации отправляется `PATCH` с `isActive: false`.

Все ссылки на stage, source и Meta campaign launch проверяются по тому же `workspace_id`, что и заявка. Ссылка на объект другой клиники возвращает validation error.

## Backfill и attribution

В историческом backfill 019 статусы нормализуются в четыре semantic-группы.
Новый UI также распознаёт `postponed`, `deferred` и русские формы «отложена» /
«отложенные» как пятую группу. 080 не переписывает старые заявки. Пустой или
неизвестный legacy-статус по-прежнему получает `new`. Источники сопоставляются
с дефолтами по точным известным вариантам, остальные получают legacy-источник.

Campaign attribution намеренно консервативна. `meta_campaign_launch_id` заполняется только при одном точном совпадении в том же workspace по внутреннему ID, реальному Meta campaign ID или уникальному точному имени реального запуска. Неоднозначные значения остаются `null`.

В следующих версиях `meta_campaign_launch_id` станет основой source/campaign attribution, но CRM6 не добавляет предположительные рекламные метрики.

## UI и fallback

`/leads` загружает этапы и источники из API. Демо-fallback содержит пять статусов
и свободный текст источника. При успешной загрузке настоящего справочника UI
показывает только его активные этапы: он не подставляет фиктивный postponed ID
в базу, где 080 и явное заполнение ещё не выполнены. Legacy/localStorage заявки
продолжают отображаться через regex-normalization.

AI Control Center сначала использует `semanticGroup`, затем legacy status fallback. Метрики остаются rule-based, без AI-прогнозов и выдуманной выручки.

## CRM7 — Campaign attribution UI

CRM7 добавляет ручную привязку заявки к реальному рекламному запуску: поле
«Рекламная кампания» в форме добавления/редактирования заявки на `/leads`.

- Список кампаний берётся из существующего `GET /api/crm/meta-launches`
  (в demo-режиме — из локальной истории запусков). Новых endpoint'ов нет.
- Предлагаются только безопасные записи: dry-run/тесты, неудачные запуски и
  записи без названия исключаются. Подпись — название кампании, услуга/город,
  дата и статус «создана выключенной». Сырые payload, Meta ID и URL в
  клиентском режиме не показываются.
- Выбранная кампания сохраняется в `leads.meta_campaign_launch_id` через
  существующий dual-write (CRM6): сервер проверяет, что запуск принадлежит
  тому же workspace, и заполняет snapshot `campaign` названием кампании.
  «Не выбрана» очищает связь (`null`).
- Текстовое поле «Кампания / услуга» остаётся для совместимости; при выборе
  запуска и пустом тексте оно заполняется названием кампании.
- Карточка/деталь заявки показывают понятную подпись кампании или
  «Кампания не связана». В admin-режиме — только `meta_campaign_launch_id
  present: yes/no`.
- AI Control Center показывает «Атрибуция рекламы: Частично готово», когда
  отвечают endpoints заявок и запусков.

`meta_campaign_launch_id` — основа будущей аналитики source/campaign.
Продажи, CPL и метрики эффективности кампаний — future scope: CRM7 не
считает выручку и не добавляет предположительные рекламные метрики.

## CRM8 — Attribution metrics foundation

CRM8 добавляет первые безопасные метрики атрибуции — только подсчёт заявок по
наличию `meta_campaign_launch_id`, без бэкенд-изменений.

**Что считается:**

- `/leads`: компактная сводка «Связаны с рекламой: N · Без рекламной
  кампании: M» и вторичный фильтр «Реклама: Все / С рекламой / Без рекламы».
  Фильтр работает поверх фильтра этапов и поиска, не заменяя их.
- AI Control Center: количество заявок без атрибуции. Если такие есть,
  появляется rule-based рекомендация «Свяжите заявки с рекламными
  кампаниями» с пояснением «Это поможет позже считать эффективность
  рекламы». Нет заявок или все связаны — рекомендация не показывается.

**Что не считается (future scope):**

- продажи, выручка, CPL, ROI/ROMI и любая эффективность кампаний;
- расход рекламного бюджета и связка с Meta Insights;
- автоматическая (fuzzy) атрибуция — связь остаётся ручной через CRM7 UI.

Метрики — чистый подсчёт по существующим данным заявок; API, миграции и
логика Meta launch не менялись.
Полноценный модуль продаж/deals остаётся future scope.
