# Приход означает оплату

Правило согласовано владельцем: подтверждение прихода оформляет оплаченную
продажу на стоимость услуг записи. Выручка по-прежнему считается из `deals`
со статусом `paid`, по дате `paid_at`, а не из всех созданных записей.

## Безопасное включение

Миграция `061_appointment_arrival_payment.sql` добавляет правило, но **не включает
его ни для одного пространства**. `workspaces.arrival_marks_paid` по умолчанию
`false`. Применение миграции, публикация приложения и включение правила для
конкретной клиники требуют отдельного согласования. Рабочие салоны не являются
тестовой средой. В текущей реализации нет публичного переключателя настройки.

После отдельного разрешения включать флаг только у проверенного workspace UUID.
Не выполнять массовое обновление workspaces. Перед включением проверить записи
без цены и наличие нескольких продаж по одной записи. Не исправлять финансовую
историю автоматически. Все тесты выполняются в изолированной памяти PGlite.

## Поведение

- INSERT со статусом `arrived` или переход в него создаёт продажу в той же
  транзакции, что и подтверждение прихода.
- Используется `appointments.price_minor`: снимок согласованной общей стоимости,
  включая несколько услуг. Валюта KZT, сумма в тиынах. Текущий прайс не перечитывается.
- Неизвестная цена (`null`) запрещает операцию целиком; явно заданный ноль допустим.
- Единственная ожидающая продажа переходит в `paid`; её связи и атрибуция сохраняются.
- Уже оплаченная продажа сохраняет первоначальные сумму и дату оплаты.
- Несколько существующих продаж, отменённая/возвращённая продажа без закреплённого
  чека или другая валюта ожидающей продажи требуют ручной проверки.
- `arrival_sale_id` возвращается только как серверное поле. Карточка показывает
  «Продажа оформлена» вместо предложения создать вторую продажу.
- Повторное подтверждение, смена статуса назад или редактирование записи не
  создают повторную оплату. После оформления изменение цены визита не переписывает
  финансовую историю. Исправлять продажу и возврат следует отдельно в продажах.
- Нет фоновой оплаты старых посещений. В пространствах с выключенным флагом
  сохраняется ручное оформление продажи.

## Защита

Триггеры работают с правами вызывающей стороны, без `SECURITY DEFINER`.
Существующая серверная проверка доступа к своей записи остаётся обязательной.
Доступ мастеру ко всем продажам не выдаётся. Ручная вставка/перепривязка продажи
блокирует ту же строку записи; в включённом пространстве второй связанный чек
отклоняется. Закреплённую продажу нельзя отвязать. Отказ в создании продажи
откатывает и смену статуса записи. Ошибки БД переводятся в сообщения из allowlist.

При ответе на сохранение API перечитывает запись после AFTER-триггера, поскольку
первоначальный RETURNING ещё не содержит ссылку на чек. Выручка и её показатели
используют существующие правила Sales/AI Control Center без новых формул.

## Проверки

`pnpm run test:arrival-payment` выполняет миграцию и операции на настоящем
Postgres-движке PGlite в памяти. Покрывает суммы, ноль/неизвестную цену, повтор,
отмену/возврат, ожидающую/оплаченную продажу, межклинические связи и отключённый
режим. Тесты последовательные: перед согласованным выпуском конкурентные
транзакции дополнительно проверяются на отдельном PostgreSQL и preview-развёртывании.

Не применено в production. Миграция сама не меняет цены, аккаунты, сессии,
существующие продажи или правила Meta-рекламы.
