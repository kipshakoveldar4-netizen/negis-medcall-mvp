# CRM server auth foundation

CRM11-auth добавляет серверную проверку администратора для будущих чувствительных операций Negis OS. На этом этапе существующие CRM-маршруты не закрываются массово: foundation используется новым диагностическим маршрутом и готов для повторного применения в следующих задачах.

## Модель доверия

- `localStorage` остаётся только UX-состоянием интерфейса. Значения роли, workspace и режима из браузера не являются доказательством прав на сервере.
- Защищённый запрос передаёт `Authorization: Bearer <Supabase access token>`.
- Сервер проверяет токен через `supabase.auth.getUser(token)`.
- После проверки пользователя сервер ищет активную строку `staff_users` по `auth_user_id`, `workspace_id` и `status = active`.
- Доступ получают только роли `owner` и `admin`.
- Demo/localStorage-сессия не получает доступ к защищённым операциям.

Токен, service role key и исходные ошибки Supabase не возвращаются клиенту и не должны попадать в логи.

## Диагностический маршрут

```text
GET /api/crm/auth-context?workspaceId=<uuid>
Authorization: Bearer <Supabase access token>
```

Успешный ответ содержит только безопасный контекст:

```json
{
  "success": true,
  "mode": "supabase",
  "data": {
    "workspaceId": "<uuid>",
    "role": "owner",
    "staffUserId": "<uuid>",
    "isAdmin": true
  }
}
```

- `401` — токен отсутствует, истёк или не прошёл проверку Supabase.
- `403` — пользователь существует, но не имеет активной роли `owner/admin` в запрошенном workspace.
- `503` — серверная конфигурация Supabase или проверка членства временно недоступна.
- Маршрут не переключается в demo mode и не доверяет `workspaceId` или роли из localStorage.

## Admin Center

Admin Center получает текущий access token через Supabase SDK и отдельно вызывает `/api/crm/auth-context`. Интерфейс показывает один из безопасных статусов:

- `Админ-доступ подтверждён`;
- `Нужно войти заново`;
- `Недостаточно прав`.

Проверка не блокирует всё приложение. Она показывает готовность защищённых административных операций, а существующий клиентский route guard остаётся UX-навигацией.

Текущий login-flow временно сохраняет совместимый поиск профиля сотрудника по email. Это не расширяет серверные права: любой чувствительный endpoint независимо проверяет Supabase Bearer token и связывает пользователя со `staff_users` только через `auth_user_id`.

## Следующие защищённые операции

`requireWorkspaceAdmin` должен применяться сервером к следующим чувствительным маршрутам по мере их реализации:

- ручная синхронизация Meta Insights;
- чтение фактических расходов кампаний;
- изменение production-интеграций;
- управление секретозависимыми настройками;
- административные действия над сотрудниками и workspace.

Первые планируемые маршруты на этой основе:

- `POST /api/crm/meta-insights-sync`;
- `GET /api/crm/meta-campaign-insights`.

Планируемые Meta Insights endpoints не реализованы в CRM11-auth. Перед их добавлением в production также нужно применить migration 021 и проверить таблицы `meta_campaign_insights` и `meta_insights_sync_runs`.
