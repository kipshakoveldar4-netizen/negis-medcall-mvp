## Corrected Observation And Baseline

C32 sampled two shell caches at controllerchange. Diagnostic local tracing
showed that controllerchange can precede completion of activate/waitUntil.
That early sample did NOT alone prove eviction failure; the final real test
now waits for controller.state=activated before checking caches. Temporary
trace wrappers were removed; the final fixture alters only the worker BUILD_ID.

Independently, the [real-source VM regression](../scripts/src/medina-service-worker-cache.test.ts)
deterministically held a navigation or immutable-asset network response, activated
a new worker which deleted the old cache, then released the old response. The
original source reopened its old cache after the wait in both cases. Its global
asset lookup also returned bytes from an unrelated named cache. Baseline:
**1 pass / 3 fail**, no skips. No external transport was used.

Capturing a handle before the network wait addresses that first race, but a
retired event or activation between ownership read/open also needs a fence.
Synthetic tests model those boundaries explicitly; they are not described as
separately reproduced native-browser schedules.

## Narrow Worker Contract

- Activation writes only the public build identifier to `medina-active-shell`
  at an internal cache key, then removes retired `medina-shell-*` names and
  claims clients. This extra cache contains no account, role, token or CRM data.
- Before opening a shell cache, read the active identifier. Recheck after open;
  if retirement happened during open, remove only this worker's old name. Keep
  the returned Cache handle across the network wait, never reopen after it.
  Writing a deleted retained handle cannot resurrect the name.
- Immutable assets and offline navigation read only this shell cache, not any
  matching response from unrelated named caches. Navigation remains network-first;
  a failed network with no owned shell returns Response.error, not foreign HTML.
- API/auth/no-sw/external/non-GET and ordinary non-shell requests return before
  touching CacheStorage or fetch. PAUSED/ACTIVE, SDK/auth and provider paths are
  not modified. Push/message/notification routes and update consent are unchanged.
- Cache open/match/put failures degrade to an online response; failed caching
  cannot discard a successful network result. Non-ok navigation cannot replace
  the shell. Storage failure during activation does not block clients.claim.

## Remaining Boundary

This only accepts the owned local worker sequence and modeled races. It cannot
retroactively fence an already deployed legacy worker with no ownership logic;
first upgrade/rollback and offline recovery from that older version need their
own exact-built/served test. Other same-origin code can access CacheStorage:
the build marker is a correctness fence, not an authorization/XSS boundary.
Installed standalone, iOS/WebKit/physical devices, offline reconnect and every
route/role/form are not accepted by these cases. Current isolated Preview and
the other G1-G8 gates remain in the release matrix; there is no 100% claim.
